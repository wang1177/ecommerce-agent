# 电商客服 Agent

一个基于 **ReAct 循环 + Function Calling** 的电商客服处理系统。

模型不是按固定流程走，而是**自己决定**：要不要查订单、查不到怎么办、
要不要查政策、什么时候转人工。

---

## 快速开始

```bash
# 1. 安装依赖（建议用国内镜像）
pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

# 2. 配置 API Key（环境变量）
set DASHSCOPE_API_KEY=sk-xxxxxx           # Windows CMD
$env:DASHSCOPE_API_KEY="sk-xxxxxx"        # PowerShell

# 3. 建库（生成 orders.db，12 条模拟订单）
python init_db.py

# 4. 启动
python main.py

# 5. 打开浏览器
# http://127.0.0.1:8001
```

## 它能做什么（5 个典型场景）

| # | 输入 | Agent 的行为 |
|---|---|---|
| ① | `订单 ORD202407150001 到哪了？` | 查订单 → 报出承运商和物流单号 |
| ② | `ORD202407150005 怎么还没发货？` | 查订单（发现超时）→ **再查政策** → 报出"可申请 5% 补偿，约 17.9 元" |
| ③ | `我上周三买的耳机还没发货，订单号 ORD2023101 开头` | 尝试查（号不全失败）→ **不编造订单号**，转而请用户提供 12 位完整号 |
| ④ | `买的东西有质量问题，能退吗？` | 查政策 → 按原文答"签收 15 天内可换新或全退" |
| ⑤ | `再不退款我就去投诉你们！` | **1 步**转人工，reason 记录"用户威胁投诉，情绪激动" |

⭐ 场景 ②③⑤ 是固定链路做不到的：
- ② 需要"查完订单再决定要不要查政策"的多步决策
- ③ 需要在工具失败后**改变策略**而不是硬生成
- ⑤ 需要识别情绪并主动终止

## 架构

```
用户输入
   ↓
┌──────────────────────────────────────────┐
│  ReAct 循环（最多 5 步）                  │
│                                          │
│  ① 死循环检测                            │
│  ⑤ 时间超时检查 / ④ token 预算检查        │
│      ↓                                   │
│  模型决策（Function Calling）             │
│      ↓                                   │
│  ② 工具结果截断  →  ③ 异常兜底            │
│      ↓                                   │
│  执行工具 → 结果回填 → 下一轮              │
└──────────────────────────────────────────┘
   ↓
{answer, trace, steps, reason}
```

## 三个工具

| 工具 | 作用 | 关键设计 |
|---|---|---|
| `lookup_order(order_id)` | SQLite 查订单 | ⭐ 返回 `hours_since_pay` + `overdue`——把"是否超时"算在代码里，不让模型算日期；⭐ 用**小时**而非天，因为政策是"48 小时"，用整数天会判错边界 |
| `search_kb(query)` | 读政策条款 | 政策只有 6 条，直接返回全文；库大了再换 RAG 检索 |
| `escalate_to_human(reason)` | 转人工 | 调用即终止循环 |

**订单号格式：`ORD` + 12 位数字 = 15 位**（如 `ORD202407150001`）。
`tools.py` 用正则 `^ORD\d{12}$` 校验，而不是 `len()` —— `len()` 只能挡"太短"，
挡不住格式错（字母前缀、位数不对）。

## 多轮对话

`run_agent(question, llm, history=None, max_turns=3)`

- **`history`**：`[{"role": "user"/"assistant", "content": str}, ...]`，会按顺序
  塞成 `HumanMessage` / `AIMessage` 放进上下文
- **`max_turns=3`**：只保留最近 3 轮。⭐ 这是有意的上下文工程 —— Agent 每轮都要
  把完整 messages 再发一次，历史越长成本越高，而早期对话对当前问题通常没用

### ⭐ 订单号锚定（防多轮幻觉）

**实测发现的问题**：多轮对话里模型会把 `ORD202407150001` 记成 `ORD202307150001`
（错一位），然后拿错误的号去查，再告诉用户"查不到"。

**解法不是为了提示词加约束，而是在代码层面消除不确定性**：

```python
known_ids = _collect_order_ids(*历史内容, 当前问题)   # 正则机械提取
messages[0] = SystemMessage(SYSTEM_PROMPT +
    "\n【本轮可用订单号（只能从这里原样复制，不得改写任何一位）】\n" +
    "\n".join(known_ids))
```

把"回忆"变成"复制"。验证：

| 输入 | 不带历史 | 带历史 |
|---|---|---|
| `它什么时候能到？` | 反问"请提供订单号" | ✅ 正确答出 `ORD202407150001` 的物流信息 |

**这个对比就是"历史真的进了上下文"的证据**（不是只在前端显示）。

## 防护（两个视角）

Agent 的防护不是一套固定清单，而是**按失败模式 + 资源维度**两个视角配的。

### 视角一：按失败模式

| 防护 | 位置 | 防什么 |
|---|---|---|
| **① 死循环检测** `_is_looping` | 每轮循环**开始前** | 模型反复用相同参数调同一工具，白烧 5 步和 token |
| **② 结果截断** `_truncate` | 工具结果**回填上下文前** | 一次工具返回几千字把上下文撑爆 |
| **③ 异常兜底** `_safe_call` | 包住**每一次**工具调用 | 工具报错导致整个 Agent 崩掉 → 改成把 error 回传给模型，让它自己换策略 |

### 视角二：按资源维度

| 资源 | 上限 | 触发后 |
|---|---|---|
| **圈数** | `MAX_STEPS = 5` | 跑满即收口（`max_steps`） |
| **内容量** | `TOKEN_BUDGET = 8000` | 超预算收口（`token_budget`） |
| **时间** | `TIME_BUDGET = 30` 秒 | 超时收口（`timeout`） |

**⭐ 为什么时间和 token 都要有 —— 两者正交：**

```
token 管"内容量"，时间管"等了多久"，不能互相代表：
  · 一次模型调用卡住 15 秒，token 可能只涨几十  → token 闸看不见
  · 反向：模型秒回但连转 5 圈，token 涨很多但总时长可能只有 10 秒
        ↓
所以两者都要：token 是成本维度，时间是体验维度（用户等不了 30 秒）
```

**⚠️ 时间超时是【轮间检查】，不是【请求级超时】：**

如果某一次 `llm.invoke` 本身卡了 40 秒，只能等它返回后才发现超时。
真正的硬超时需要给 SDK 传 `timeout` 参数，或用线程池 + `future.result(timeout=...)` 包一层。
这是当前实现的已知局限。

**⚠️ `TOKEN_BUDGET=8000` 在当前配置下是【临界防护】：**

实测 5 圈批量查 5 个订单真实消耗 10735 token（差 100 未触发）。
因为 `MAX_STEPS=5` + 单次截断 800 字已让 token 上限约 11000、波动仅 20%~40%，
所以这道闸挡的是"圈数不多但内容特别重"的情况；若把 `MAX_STEPS` 调大，它才会变成主力。

### 三个值得说明的设计选择

**1. `window=1` 而不是 2**

本项目的三个工具都是**确定性**的（SQLite 查询、读文件、返回固定标记），
同样参数必然得到同样结果 —— 所以模型用相同参数重试一次毫无价值，应当立刻收口。

`window=1` 在第 3 步就能拦下，比 `window=2`（第 5 步）省 2 次模型调用。
实测：注入"连续相同调用"的 mock，3 步收口，reason=`loop_detected`。

⚠️ 如果工具是非确定性的（查实时库存、调外部 API 有波动），应改成 `window=2`
—— 那时"重试一次"确实可能有意义。

**2. 截断要标注"已截断，原长 N 字"**

如果悄悄截断，模型会以为这就是全部内容，可能给出不完整的回答。
明确告知后，它才可能换个更精确的 query 再查一次。

**3. 工具异常返回 error 而不是抛出**

把异常翻译成模型能理解的反馈，它就能自己换策略
（查订单失败 → 转去查政策 → 再追问用户），而不是整个流程崩掉。

## 界面

```
┌─────────────────────────────┬──────────────────┐
│  对话（多轮历史）             │  执行轨迹（trace） │
│                             │                  │
│  用户：ORD...001 到哪了？     │  第1步            │
│  助手：已发货，顺丰 SF123...  │  → lookup_order   │
│                             │  参数：{...}      │
│  用户：那 ORD...005 呢？      │  返回：{...}      │
│  助手：可申请 5% 补偿 ≈17.9  │                  │
│                             │  第2步            │
│  ┌───────────────────────┐  │  → search_kb     │
│  │ 输入框（发送后自动清空） │  │  ...             │
│  └───────────────────────┘  │                  │
│  [发送] [清空]               │  共3步·2次工具调用 │
└─────────────────────────────┴──────────────────┘
```

**为什么用 Gradio 而不是手写 HTML：**
- 多轮历史、发送后清空输入框、左右分栏 —— Chatbot 组件原生支持
- 和另一个 RAG 项目的技术栈一致，复用熟悉的组件
- trace 部分用 `gr.HTML` 渲染，和手写 HTML 的工作量相当

**一个服务两个入口**（`gr.mount_gradio_app`）：
- `http://127.0.0.1:8001` → Gradio UI
- `http://127.0.0.1:8001/chat` → HTTP API

## 已知边界

1. **订单数据是模拟的**（12 条，写死在 `init_db.py`）。
   `lookup_order` 是独立函数，换真实订单库只改这一处，Agent 侧一行不用动。
2. **政策检索没有走向量检索**——6 条政策只有几百字，直接整篇返回更可靠。
   政策库大了应该换成 RAG 检索（按 query 召回相关条款）。
3. **多轮历史只保留最近 3 轮**——再早的会被丢掉。对客服场景够用，但如果用户
   在很长的对话后回头问早期订单，会丢失上下文。可考虑改成"摘要 + 最近 N 轮"。
4. **历史里不保留工具调用详情**——只放最终的 `AIMessage`，不放 `ToolMessage`。
   这样能省 token，但模型无法回溯"上一次具体查了什么参数"。
5. **没有并发控制**——`/chat` 用 `def` 交给 FastAPI 线程池，
   但没有限制同时调用 DashScope 的并发数，高并发会撞限流。
6. **没有做效果评测**——目前只靠 5 个手写场景 + 12 个单测做功能验证。
   严格做法应该有一批标注反馈，对比固定链路与 Agent 的正确率/步数/延迟/成本。
